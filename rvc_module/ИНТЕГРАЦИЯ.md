# Подключение модуля RVC

RVC берёт JSON от сканеров (атакующий + Trivy + инвентаризация хоста) и
собирает отчёт о реально воспроизводимых уязвимостях. Работает отдельно,
ничего из основного проекта не импортирует. Связь только через JSON-файлы,
так что подключается без переплетения с вашим кодом.

## Требования

- Python 3.11 или новее.
- Flask — только если нужен веб-дашборд: `pip install -r requirements.txt`.
- Интернет не нужен. Веб-страница тянет шрифты с Google Fonts; без интернета
  подставляется системный моноширинный, на работу это не влияет.

## Состав

    rvc/
      models.py        структуры данных
      loaders.py       чтение трёх наборов JSON -> ScanContext
      knowledge.py     доступ к локальному срезу MITRE
      mitre_kb.json    срез баз MITRE (CVE/CWE/CAPEC/ATT&CK)
      engine.py        движок: 5 проверок реализуемости
      enrichment.py    обогащение MITRE + сборка плейбука
      pipeline.py      сборка отчёта + запуск из консоли
    app.py             веб-сервер (Flask)
    web/index.html     дашборд (одна страница)
    report.json        пример выходного файла
    requirements.txt

## Куда положить

Распаковать в корень проекта или в подпапку (например `tools/rvc/`). Папку
`rvc/` не разбивать — она импортируется как пакет.

## Входные данные

Модуль читает три набора файлов относительно базовой папки:

    data/trivy_scan_*.json          отчёты Trivy, берётся самый свежий по имени
    data/scan_history/scan_*.json   инвентаризация хоста, самый свежий
    history/**/*.json               сканы атакующего, берутся все и объединяются

Имена файлов содержат дату-время, поэтому "самый свежий" определяется
сортировкой по имени. Сканы атакующего объединяются: открытые порты — в
объединение, векторы атак — с удалением дублей по (имя, порт).

## Вариант 1. Консоль, отчёт в JSON

    python -m rvc.pipeline --base . --out report.json

    --base   папка со стендом, где лежат data/ и history/ (по умолчанию корень модуля)
    --out    куда записать отчёт

В консоль печатает счётчики: реализуемо / частично / отклонено.

## Вариант 2. Вызов из своего кода

    from rvc.pipeline import build_report

    report = build_report("/путь/к/стенду")   # возвращает обычный dict
    realizable = report["realizable_vulnerabilities"]
    rejected   = report["rejected"]

Тот же dict можно отдать в ваш API, сохранить в БД или дописать в общий отчёт.
Объект MITRE-базы можно загрузить один раз и переиспользовать:

    from rvc.knowledge import Knowledge
    kb = Knowledge()
    report = build_report(base_dir, kb)

## Вариант 3. Веб-дашборд

    pip install -r requirements.txt
    python app.py
    # http://127.0.0.1:5000

app.py отдаёт страницу и эндпоинт `/api/report`. Отчёт считается при первом
запросе и кэшируется. Пересчёт — кнопка "Обновить" на странице или
`/api/report?refresh=1`.

Базовая папка в app.py — это папка самого app.py (переменная BASE_DIR).
Перенесёте app.py в другое место — держите data/ и history/ рядом или
поправьте BASE_DIR.

## Если данные лежат по другим путям

Пути собираются в `loaders.load_context(base_dir)`:

    history/                      -> load_attacker(base_dir + "/history")
    data/, data/scan_history/     -> load_trivy / load_server

Если структура другая, есть два пути: передать свою base_dir, либо вызвать
`load_attacker`, `load_trivy`, `load_server` напрямую с нужными путями и
собрать `ScanContext` вручную (см. конец loaders.py). Дальше `build_report`
не нужен — зовите `engine.assess_vector` и `enrichment.*` сами, как в
pipeline.py.

## Формат выхода

См. report.json в архиве. Верхний уровень:

    meta                        цель, версия среза MITRE, счётчики, достижимые порты
    realizable_vulnerabilities  реализуемые
    partially_realizable        требуют ручной проверки
    rejected                    отклонённые, с причиной
    trivy_summary               сводка по Trivy

У каждой находки: название, severity, порт, вердикт, уверенность, причина,
trace (результаты 5 проверок), references (CVE/CWE/CAPEC/ATT&CK с описаниями),
target_software (продукт, версия, компонент, последствие), playbook
(инструменты, шаги с командами и ожидаемыми результатами).

## База MITRE

rvc/mitre_kb.json — ручной срез под уязвимости текущего стенда. Если в нём
нет нужного CVE, находка получает вердикт "partially" с пометкой о ручной
проверке и без описаний MITRE. Чтобы покрыть больше уязвимостей — дополняйте
mitre_kb.json по образцу существующих записей: блоки cve / cwe / capec /
attack, у CVE — блок match для проверки версии (по сборке ОС или по продукту).
Можно генерировать его из официальных выгрузок NVD/CWE/CAPEC/ATT&CK.

## Что важно знать

- В наших данных Trivy сканировал репозиторий кода (package-lock и подобное),
  а не живой хост. Поэтому его CVE по умолчанию не имеют сетевого пути и
  попадают в rejected. Если у вас Trivy гоняется по реальному хосту с
  открытыми веб- или БД-сервисами, поправьте сопоставление пакет-сервис-порт
  в engine.py / pipeline.py.
- Отбор детерминированный: один вход и один срез MITRE дают один результат.
  Никакой модели в принятии вердикта нет.
- "Реализуема" означает "вектор исполним, стоит пробовать", а не гарантию
  успеха. Для атак, зависящих от конфигурации (перебор паролей, null-сессии,
  отключённая подпись SMB), итог зависит от конкретного стенда.
- Версии под Windows определяются по сборке ОС из инвентаризации
  (поле os_version, например 10.0.26200). Если поля нет, проверка версии даёт
  "unknown" и находка уходит в partially.
