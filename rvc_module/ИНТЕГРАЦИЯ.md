# Подключение модуля RVC (v2)

RVC берёт JSON от сканеров и собирает отчёт о реально воспроизводимых
уязвимостях. Работает отдельно, ничего из основного проекта не импортирует —
связь только через JSON-файлы.

**Что нового в v2 (под требования преподавателя и смежной программы):**

- Оценка считается отдельно для **трёх позиций атакующего**: внешний, внутренний
  с правами пользователя, внутренний с правами администратора («снаружи» и
  «изнутри», изнутри — по роли).
- Для каждой позиции есть **две оценки**:
  - **численная** (0..100) с полной разбивкой по параметрам и порогами — для
    сравнения со смежной программой;
  - **качественная** словом + цветом: **реализуемо / возможно / не реализуемо =
    зелёный / жёлтый / красный**, с обоснованием — для разбора со студентами.
- На каждую атаку — **методичка проведения** (фазы, команды, ожидаемый результат,
  пояснение, инструменты, траблшутинг) и **методичка защиты** (детект, харднинг,
  патч, проверка). Всё в JSON и на дашборде.

## Требования

- Python 3.11+.
- Flask — только для веб-дашборда: `pip install -r requirements.txt`
  (без Flask поднимается встроенный http.server, дашборд тоже работает).
- Интернет не нужен (шрифты тянутся с Google Fonts, без них — системный моно).

## Состав

      mitre_kb.json         срез баз MITRE (CVE/CWE/CAPEC/ATT&CK)
      positions.py          три позиции атакующего (модель угроз)

      methodics.py          сопоставление вектор->семейство, доступ к методичкам
      methodics_kb.json     методички атаки и защиты + профиль выполнения
      build_methodics_kb.py сборщик methodics_kb.json (источник правды, офлайн)

    web/index.html          дашборд (intro-анимация + окно оценки)

## Входные данные

Поддерживаются два контракта (определяется автоматически):

**Новый (как в этом репозитории):**

    tools/history/**/*.json   единый формат отчётов (PortScan/Parallel/analyze):
                              { target_ip, open_ports[], attack_vectors[], os_detection, ... }

Отдельной инвентаризации хоста и Trivy здесь нет. Поэтому представление о сервере
**синтезируется** из наблюдаемых открытых портов: достижимым считается ровно то,
что увидел сканер; флаги сервисов выводятся из номеров портов. Версии ПО и
средства защиты при этом считаются **неизвестными**, а не отсутствующими — это
отражается «мягким потолком» оценки (см. ниже).

**Классический (если есть инвентаризация):**

    data/trivy_scan_*.json          отчёты Trivy (самый свежий)
    data/scan_history/scan_*.json   инвентаризация хоста (самый свежий)
    history/**/*.json               сканы атакующего (все, объединяются)

## Запуск

**Консоль:**

    python -m rvc.pipeline --base tools --out report.json

Печатает счётчики реализуемо/возможно/не реализуемо по каждой из трёх позиций.

**Из своего кода:**

    from rvc.pipeline import build_report
    report = build_report("tools")          # обычный dict
    for f in report["findings"]:
        ext = f["assessments"]["external"]["numeric"]["score"]      # 0..100
        word = f["assessments"]["external"]["qualitative"]["label"] # реализуемо/возможно/...

**Веб-дашборд:**

    python app.py            # http://127.0.0.1:5000
    # базовая папка по умолчанию — ./tools ; переопределяется RVC_BASE_DIR

Дашборд показывает intro-анимацию, затем окно: слева — структурированный список
атак (со словами и цветами по трём позициям), справа по клику — полная оценка,
численная разбивка и методички. Числа по умолчанию скрыты под словами и
открываются по наведению/кнопке.

## Формат выхода (схема 2)

    meta
      rvc_version, report_schema=2, generated_with_llm:false
      target, host_inventory ("synthesized_from_ports" | "from_scan_history")
      reachable_ports
      positions[]            описание трёх позиций
      scoring_model          самоописание численной модели (база, пороги, факторы, гейты)
      counts.by_position     счётчики реализуемо/возможно/не реализуемо по позициям
    findings[]
      attack_name, attack_type, port, service, family, family_title
      methodic_basis         product | type | generic (на чём основана методичка)
      methodic_basis_label   человекочитаемая пометка основы
      target_software        продукт/версия/компонент/последствие
      references             CVE/CWE/CAPEC/ATT&CK из локального MITRE
      assessments
        external | internal_user | internal_admin
          severity
          numeric            score(0..100), base, raw_sum, soft_cap_applied,
                             verdict, band, thresholds,
                             factors[]{ key, label, delta(+/-), evidence },
                             gates[]{ key, evidence }
          qualitative        label, color (green/yellow/red), justification,
                             verify[] — что уточнить, чтобы подтвердить (для жёлтого)
      methodic               summary, prerequisites, phases[]{steps[]{action,command,expected,explanation}},
                             tools, troubleshooting, cleanup
      defense                summary, detection, hardening, patch, validation

### Численная модель (для сравнения со смежной программой)

Всё описано в `meta.scoring_model`, расчёт — в `scoring.py`:

- База **50**. К ней прибавляются/вычитаются факторы, каждый с величиной (`delta`)
  и уликой (`evidence`). Итог ограничен 0..100.
- Факторы: достижимость (+4..+18 или гейт), живой сервис (-8..+10), версия/продукт
  (+15 при подтверждении, -6 при неизвестности, гейт при опровержении), зрелость
  эксплойта (+2..+14), соответствие привилегий роли (-28..0), компенсирующие
  контроли (-10..0), тяжесть/CVSS (0..+8).
- **Гейты** (жёсткие отсечки -> «не реализуемо» независимо от баллов): сервис/узел
  недостижим из позиции; нужна L2-позиция/доступ к хосту, которых нет; целевой
  продукт/версия опровергнут (например, не тот продукт или пропатчено).
- **Мягкий потолок (-> «возможно»/жёлтый)**: балл ограничивается 64, если нельзя
  подтвердить версию/патч ИЛИ исход зависит от непроверяемого по данным сканера
  (пароль при переборе, реальное наличие беспарольного доступа, отключённая
  подпись и жертва). Тогда в `qualitative.verify` — что нужно уточнить.
- **Пороги** (тоже в JSON): `>= 65` — реализуемо (зелёный); `35..64` — возможно
  (жёлтый); `< 35` или сработавший гейт — не реализуемо (красный).

Качественная оценка (слово+цвет) выводится из балла и гейтов детерминированно —
один источник истины, полностью воспроизводимо.

### Позиции атакующего

- **external** — снаружи, без доступа: достижимы только опубликованные сервисы;
  периметровые средства применимы; атак с L2-позицией (relay/MITM) и локальных
  действий (дамп SAM) нет.
- **internal_user** — инсайдер с правами пользователя: достижимы внутренние
  сервисы и L2-атаки; привилегированные действия требуют повышения прав.
- **internal_admin** — инсайдер-администратор: ограничения по привилегиям сняты
  (потолок воздействия скомпрометированного админа).

## Методички (работают на ЛЮБОМ стенде)

Софт запускают на разных машинах с разными данными сканеров, поэтому описание
строится СЛОИСТО (см. `methodics.py`), и методичка есть всегда:

1. **product** — продукто-специфичное семейство (совпадение по CVE или алиасу
   в имени): точная методичка (EternalBlue, Zerologon, MySQL, vCenter…).
   16 семейств в `methodics_kb.json` -> `families`.
2. **type** — обобщённая методичка по КЛАССУ атаки (по `attack_type`): корректная
   универсальная (RCE/brute/relay/credential_theft/…), когда конкретного
   семейства нет. НЕ подменяется чужим продуктом. 15 типов в `type_methodics`.
3. **generic** — общий порядок исследования, когда тип не распознан вовсе
   (`type_methodics._default`).

Основа отражена в `finding.methodic_basis`. На дашборде — пометка у методички
(«под конкретный продукт» / «обобщённая по типу атаки» / «общий порядок»).

Профиль выполнения (привилегии/LAN/зрелость) тоже берётся слоисто — это даёт
объективную численную оценку даже для незнакомых сервисов (например, чужой
relay_attack -> требует L2-позиции -> снаружи красный, изнутри зелёный).

База правится через сборщик `python -m rvc.build_methodics_kb` (исходник
`build_methodics_kb.py`). Чтобы добавить точную методичку под свой сервис/CVE —
добавьте семейство в `families` (и при необходимости CVE в `mitre_kb.json`).
Чтобы расширить обобщённый слой — добавьте/поправьте запись в `TYPE_METHODICS`.

## Детерминизм и воспроизводимость

Вердикт — чистая функция от входа и срезов баз (MITRE + методички). Никакой модели
в принятии решения. Полная разбивка факторов и гейтов делает любой балл
перепроверяемым вручную.
